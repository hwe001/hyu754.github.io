1 The core concept

A "vascularly constrained functional macro-unit": bridge patient-scale anatomy (Couinaud segments, imaged vasculature — resolvable to maybe 40–90 branch generations) down toward the liver's true functional scale (~10&sup6; hepatic lobules, ~1.4 mm³ each) without meshing every lobule individually.

  • Macro — the 8 Couinaud segments. Done, real segmented geometry.
  • Meso — portal perfusion territories, each fed by one real imaged terminal branch, extended by a synthetic vascular tree toward lobule-cluster resolution. Each meso-unit's terminal flow/pressure becomes the boundary condition for a micro-scale lobule model.
  • Micro — representative lobule physics (1D portal→central oxygen/zonation PDE). Not started.

This session's work is entirely the meso layer, scoped to Couinaud segments II+III — the left lateral lobe, the standard adult-to-infant living-donor transplant graft, chosen as a tractable and clinically meaningful demo region.

3 What's built and verified

3.1 Anatomy pipeline

doneLegacy format → compact geometry.

scripts/skeleton.py parses the source Zinc/three.js JSON (vertex/face arrays, bitmask face encoding — not glTF) into {positions, indices}, and reconstructs a vessel skeleton graph from the triangulated tube surface. Each vessel mesh turns out to be ~40–90 disconnected mesh fragments, not one connected surface — the script re-bridges them into a proper node/edge graph via tuned endpoint clustering.

doneS1+S9 merge, evidence-based.

Geodesic distance along the portal vein surface graph (not straight-line, which cuts through tissue) showed S9's portal entry is topologically closest to S1's — consistent with S9 being a split-off caudate sub-region. All downstream work uses the merged 8-segment set. Whole-liver volume: 1,433,320 mm³.

3.2 Topology-based perfusion-zone identification

done6 real terminal branches confirmed for S2/S3 (scripts/find_s2s3_roots.py → data/s2s3_roots.json).

Naive nearest-vertex spatial assignment was tried first and rejected as unreliable — a terminal can sit spatially close to a segment without being the branch that actually perfuses it. Instead: BFS the portal skeleton graph from the main trunk (identified by an outlier vessel-radius test), find the deepest common ancestor of all candidate leaves near S2/S3. Result: 1 terminal in S2, 5 in S3 — independently verified via point-in-mesh containment to be genuinely inside tissue, not merely nearby.

3.3 OpenCCO integration

doneBuilt from source (DGtal + OpenCCO, C++, not a pip package) — full build recipe in HANDOFF.md §2.4, ~5 min total on standard Ubuntu packages.
doneDomain confinement fixed and verified.

Real bug found: DGtal's .vol reader places the domain origin at Center − (dim−1)/2, not at index (0,0,0), for whatever Center is given — every territory file was written with Center=(0,0,0), silently offsetting the domain by roughly half its own size. Synthetic trees spilled up to 60+ mm outside the real mesh (83% of node endpoints). Fixed in run_opencco.py. Re-verified by point-in-mesh containment testing after the fix: 97.5% of node endpoints strictly inside, remainder within 0.8 mm of the surface (voxel discretization noise, not a leak).

doneExporter switched from .txt to .xml.

OpenCCO's -e/.txt exporter resolves each segment's parent via a fragile raw array-position lookup; the -x/.xml exporter uses an explicit ID-referenced node/edge table (scripts/xml_helpers.py). More robust architecture, and replaces a "guess the nearest node" root-connector heuristic with OpenCCO's own definitive root point.

verified, not the bugTree topology/connectivity.

A rigorous re-investigation (ID-based BFS from the root, not spatial-proximity clustering — scripts/check_id_bfs.py) confirmed the tree was fully connected all along, in both the old and new exporters, at every scale tested including the real 3,542-terminal trees. The earlier "floating subtree" alarm was a false positive: checking 3D spatial proximity is not the same as checking graph connectivity — two unconnected nodes can legitimately sit close together in space. The XML switch was worth keeping regardless, but it is not what's wrong with the tree (see §4).

doneDensity pushed to 10+ generations.

50 mm³/terminal → 3,542 synthetic terminals, 7,084 segments across the 6 territories. Cross-checked against a closely related published paper (§6) — lands in the same ballpark (~15–35 lobules represented per terminal in both, arrived at independently).

3.4 Flow/pressure solve

importantOpenCCO's own flow/pressure/resistance values are unusable.

my_pPerf=13300, my_pTerm=8400, my_qPerf=8330 are literally OpenCCO's unmodified coronary-artery demo defaults, hardcoded, not derived from our -a/-n inputs at all — confirmed in its own XML output and in CoronaryArteryTree.h source. Its per-segment radius is trustworthy (genuinely Poiseuille/Murray's-law optimized); its flow/pressure bookkeeping is not.

doneIndependent Poiseuille network solve (scripts/compute_flow.py).

Real mm geometry + literature portal physiology: 1100 mL/min total portal flow, 7 mmHg portal pressure, 3.6×10³ Pa·s blood viscosity (matches OpenCCO's own internal choice). Territory inlet flow ∝ volume fraction of total liver; equal split across a territory's own terminals. Output: data/opencco_s2s3_flow.json (every segment) and data/meso_unit_terminals.json — 3,542 rows, one per meso-unit, each with position/radius/flow/pressure: the literal macro→meso boundary-condition table.

Result: terminal flow is very uniform (~0.0383–0.0384 mL/min) — a direct consequence of both terminal count and flow being assigned proportional to volume, worth stating honestly rather than presenting as an emergent finding. Pressure drop across the resolved tree is small (6.6–6.95 mmHg from a 7 mmHg root), physiologically plausible since most of the real portal-to-hepatic-vein drop is expected at the sinusoidal bed — downstream of everything modeled so far.

unfinishedPressure/flow color-coding in the viewer.

InstancedMesh setColorAt confirmed supported in three.js r0.128.0. Partially wired into viewers/meso_unit_viewer/viewer.html — button handlers and the stats footer are not yet connected. Check current state before assuming it works.

4 The open problem

This is the actual task. Everything above is context.

"OpenCCO tree usually has one inlet, then protrude into a surface to generate branches. In this case, we've to design it more strategically. In segment II and III, use real tree to create perfusion zones, then in each perfusion zone, we've the perfusion branch generate the sub-OpenCCO tree, only in this way can we perform flow simulations."
RequirementStatus
Real tree → perfusion zonesdone
Perfusion branch generates its own sub-treedone
Sub-tree reads as a directional continuation of the real vessel, not a symmetric burst from one pointopen

Confirmed via screenshot review: each territory's tree looks like a "starburst"/"sea urchin" radiating outward from one point — not a directionally-continuous extension of the incoming real vessel. This threatens flow-simulation validity, not just aesthetics: a real vessel entering tissue continues in a consistent direction and progressively ramifies; a symmetric burst with no directional constraint may not be physically appropriate for assigning boundary conditions. Not yet root-caused or fixed — this is where a teammate is needed.

Leads worth trying

  1. Directional bias at the domain root. generateTree3D only takes a root position (-p X Y Z), no direction. Check src/helpers/GeomHelpers.h and ExpandTreeHelpers.h for whether candidate-point sampling can be restricted, near the root, to the forward half-space along the real vessel's local tangent — computable from the portal skeleton graph, which already has the parent-edge direction at each of the 6 roots.
  2. Two-stage/hierarchical growth. Grow a short directional "extension" first (root + a few terminals placed explicitly along the real tangent), then use that sub-tree's outer nodes as multiple new roots for a second, larger call to fill the rest of the territory.
  3. Reconsider territory shape. Current territories are pure nearest-neighbor Voronoi cells from only 6 seed points — large and irregular, which may itself be why the fill pattern looks unnatural. Finer sub-territories might produce more natural local growth.
  4. Check whether OpenCCO's Kamiya optimization or candidate-sampling functions accept any undocumented directionality parameter — may need a small source patch (toolchain rebuilds fast, ~5 min).

5 What not to re-investigate

Already ruled out — re-checking these would waste time:

  • Tree topology/connectivity — verified fully connected at every scale tested.
  • Geometric confinement to S2/S3 — fixed and verified (97.5% strict containment).
  • The 6 real root terminals' validity — verified both topologically and geometrically.
  • OpenCCO's radius computation — trustworthy, keep using it.

6 Relevant literature

Found via live search this session, not from memory — verify before citing in the paper.

Multiscale modeling of drug-induced liver injury from organ to lobule — npj Digital Medicine, 2025

Closest prior art. Patient-specific MRI portal geometry → CCO bridging 1.5 mm vessels to 50 µm outlets → lobule-scale drug-injury physics. ~100,000 outlets for ~1.5M real lobules (~15/outlet — same order of magnitude as our 25–35/unit, arrived at independently). Their stated limitation: simplified 2D capillary geometry — our full 3D trees are a genuine differentiator. pmc.ncbi.nlm.nih.gov/articles/PMC12185720

Dual continuum upscaling of liver lobule flow and metabolism to the full organ scale — Frontiers in Systems Biology, 2022

Different strategy: continuum homogenization, no discrete vessel geometry, ~1.4M lobule-scale grid blocks at 1 mm³. frontiersin.org/.../fsysb.2022.926923

7 How to pick this up

  1. Clone the repo, checkout claude/livermodels-repo-access-ks7sit. Everything is under virtual_twin_pipeline/.
  2. Rebuild DGtal + OpenCCO (full recipe in HANDOFF.md §2.4, ~5 min, standard Ubuntu packages). Also pip install numpy scipy trimesh.
  3. Re-run order: 
    find_s2s3_roots.py → voxelize_s2s3.py → run_opencco.py → compute_flow.py
    Each writes its output JSON; copy into viewers/meso_unit_viewer/data/ to update the live viewer, then republish via the Artifact tool to the same URL (pass the existing link back in — don't create a new one).
  4. The immediate task is §4. Everything else here is context, not a blocker.
